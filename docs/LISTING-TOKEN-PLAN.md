# Where the remaining output tokens are — and what to do

Measured 2026-09-22. This is the plan for the one remaining large optimisation:
**listing-agent output**, which is 60% of everything the workflow generates.

---

## The correction

Agent 27 is **not** where the work is. Its output pattern is already the
optimised one: it authors a single `visual-plan.json` and the renderer derives
`theme.txt`, `image-notes/` and `art-direction.md` from it. That change is done
and verified.

What agent 27 still costs is **input** — a 55,355 B spec, 13,838 tokens, the
largest single input item. But input is prefill and caches at $0.006/M against
$0.300/M uncached, so it is not what makes a run slow.

The work is in the three listing agents.

## What a listing actually consists of

Every listing is dominated by an **evidence table**, not by the copy the seller
uploads:

| Listing | Tag-evidence table | Share of the listing | The actual listing copy |
|---|---:|---:|---:|
| BOOTH (agent 20) | 1,833 tok | **50%** | 188 tok (5%) |
| Creative Fabrica (agent 29) | 1,532 tok | **34%** | 276 tok (6%) |
| Pixiv (agent 22) | 1,443 tok × **2** | **58%** | ~200 tok (4%) |

So the lever is the table, not the prose.

## Work item 1 — Pixiv emits the same table twice (~1,443 tok)

`86-silken-flourish-pixiv.md` writes the identical 23-row evidence table **twice**:

- `## PIXIV TAG EVIDENCE` — 6,013 B
- `## APPENDIX: LEDGER UPDATE` — 6,009 B

Comparing the two blocks, the only differences are one blank line and a `---`
separator. The content is the same table.

**The APPENDIX is redundant, and verifiably so.** It opens with:

> The following rows are appended to `outputs/pixiv/pixiv-tag-ledger.md` for product #86.

Those rows are **already in `pixiv-tag-ledger.md`** — checked directly: the
listing's rows are present in the ledger's 42 rows. So the APPENDIX is a manual
paste target for a step that has already happened.

**Change:** drop the APPENDIX table from the listing. Have the ledger append done
by a tool (a few lines alongside `pixiv-tag-ledger.md`, which already exists for
BOOTH as `booth_tag_ledger.py`), and have the listing reference the product
number instead of reprinting the rows.

**Saving: ~1,443 output tokens — 39% of Pixiv's entire output**, with no
information lost.

## Work item 2 — BOOTH derives 63% of its table (~1,157 tok)

The TAG EVIDENCE table is 7,334 B across 20 rows, 345 B per row. Column cost:

| Column | Bytes | Share | Derivable? |
|---|---:|---:|---|
| Font-category URL | 2,945 | 40% | **yes — from the tag** |
| Exact tag URL | 1,645 | 22% | **yes — from the tag** |
| Product-fit reason | 690 | 9% | no — observed |
| Activity and provider status | 500 | 7% | no — observed |
| Paid products / distinct sellers | 413 | 6% | no — observed |
| Tag | 331 | 5% | no — observed |
| Counts (overall + font-category) | 130 | 2% | no — observed |
| Language | 40 | 1% | **yes — from the tag** |
| Evidence tier | 20 | 0% | no — observed |

**63% of the table is a pure function of the tag** — both percent-encoded URLs
and the language. `bin/booth_evidence_table.py` already computes exactly these
columns, and is verified as a strict no-op on 47 of 48 existing listings.

The problem is sequencing: the tool **fills blanks in a table the agent already
wrote**. The URLs are still generated by the model, then verified by the tool.

**Change:** the agent emits a compact per-tag record — tag, the four observed
fields, tier, fit reason — and the tool builds the full 10-column markdown table,
including both URLs and the language. The tool becomes "build from records"
rather than "fill blanks in prose".

**Saving: ~1,157 output tokens per BOOTH listing.** The observed evidence stays
exactly as the agent recorded it; only the mechanical columns move to code.

## Work item 3 — Creative Fabrica derives 25% (~377 tok)

Same shape, smaller win: the CF table is 6,130 B across 30 rows and only 25% is
derivable, because CF's tag URLs are short (`creativefabrica.com/tag/<slug>/`)
rather than percent-encoded. `bin/creative_fabrica_tag_lookup.py` already
resolves a tag to its route.

**Saving: ~377 output tokens.**

## Why this is safe

- **The APPENDIX removal loses nothing**: the rows are already in the ledger.
- **Deriving URLs from tags cannot introduce drift**: a BOOTH tag URL *is* a
  function of the tag, which is why `booth_evidence_table.py` was written that
  way and why it is idempotent on correct files.
- **Observed evidence is untouched**: counts, paid products, distinct sellers,
  activity status, provider, tier and fit reason are all recorded by the agent
  and passed through byte-for-byte. Only the mechanical columns move.
- **The validators already check the result**: `validate_booth_listing.py` and
  `validate_creative_fabrica_listing.py` both decode and verify the URL columns,
  so a build error fails closed.

## Order of work

1. **Pixiv duplicate** — largest single win, simplest change, provably lossless.
2. **BOOTH table build** — biggest structural change; extend
   `booth_evidence_table.py` from fill-blanks to build-from-records.
3. **Creative Fabrica** — same pattern, smallest payoff.

## What is *not* recommended

- **Cutting the listing prose.** It is only 4–6% of a listing; the copy is the
  product.
- **Cutting agent 27's output.** Already at its floor.
- **Shrinking the specs to reduce input.** Input caches at 50× less and does not
  drive wall clock. Keep the prefix stable instead.
